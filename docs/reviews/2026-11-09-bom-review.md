# BOM 核对、模型调用与方向提醒审查

审查日期：2026-11-09。基线：`Marginal-Z/FAI-SMT` main，`d7bdcafdd4d36ccff39bfeaa6b42017f7c738163`（3.1.0）。本地工作目录 `D:\BOM-CHECK`，修复分支 `review/bom-rules-model-orientation`；这些改动纳入 v3.2.0，发布内容见[更新说明](../release-notes/v3.2.0.md)。

项目已有可维护的基础：读取和比较引擎分离、保留原始行与来源、比较结果有证据、云端回复有结构校验、有测试与多平台 CI。主要问题在于输入内部一致性检查不足、少数规则把不确定信息当作已确认，以及本地模型状态无法从界面核实。原项目自带测试 88 项通过、8 项跳过，但本次先加入的 12 个针对性反例中有 11 项在原代码上失败。因此“已有测试全部通过”不足以证明生产 BOM 核对规则可靠。

## 本地模型到底有没有启用

默认 `localAiEnabled=false`。下载模型不会自动开启。开启后，当前流程使用的是 **embedding 向量模型**，只给规则未匹配的物料寻找候选；如果规则已经配对，或仅一侧有未匹配项，本次不会调用模型。它不是逐行重新判定整张 BOM 的语言模型，也不能证明元件实际贴装方向。

启动遗漏的状态刷新已修复；重启后会检查本地文件状态，不再依赖先进入设置页。

新增的“运行推理自检”会真正加载模型并请求两条向量，校验返回内容。它与一次 BOM 核对的调用证据分开：自检成功不会把未调用模型的 BOM 报告标成“已使用模型”。核对页的状态、Excel 和历史元数据记录本次实际调用情况；失败时保留规则结果并显示失败。

已在 WSL Ubuntu 上对 `granite-embedding-107m-multilingual-Q8_0.gguf` 做实际测试。文件 121,020,096 字节，SHA-256 为 `15691dfe830257f569a1e3521977351d16eac18e48e414908dc98ed9b8455e07`。真实推理完成两条描述、提出一对候选，结果保持 REVIEW。该证据仅适用于此次 Linux llama.cpp 运行；本次没有单独确认计算设备选择，Windows、Android、其他模型以及 GPU 需要各自验证。

## 元件方向提醒

核对页的原因筛选增加“方向核对提醒”，覆盖 PASS、NG、复核和未匹配结果。行内有提示，点击后查看证据和位号；Excel 有独立方向列和汇总数。重复料号的后续描述也参与提醒。

| 元件证据 | 提醒内容 |
|---|---|
| 二极管、LED | A/K、器件标记和 PCB 丝印；按具体型号规格书确认 |
| 双向 TVS | 先确认双向型号及引脚定义，不能套用单向二极管极性规则 |
| 钽、电解、有极性电容 | 正负极及本型号标记，避免混淆钽和铝电解标记 |
| 仅写“电容”或只有 C 位号 | 类型信息不足，先确认有无极性 |
| IC、晶体管、排阻/网络 | Pin 1、圆点、缺口和具体引脚排列 |
| 连接器、开关、继电器、模块、传感器、变压器 | Pin 1、缺口、卡扣、开口和接触面 |
| 晶体/振荡器、电池/蜂鸣器、未知类别 | 按具体类型核对供电/引脚/机械要求，未知项人工确认 |
| 普通两端电阻、明确陶瓷/薄膜或无极性电容、DNP | 不产生泛化的正负极警报 |

提醒独立于 BOM 比较状态，不会把 PASS 改成“方向已确认”。系统没有 PCB 图像、CAD 角度、料带方向及实物检查证据，不能输出正确安装角度或替代首件检查。

规则依据包括厂商原始资料：[KEMET 有极性电容说明](https://www.kemet.com/en/us/capacitors/polymer/tantalum-polymer-faqs.html)、[KEMET T510 极性标记](https://content.kemet.com/datasheets/KEM_T2055_T510_AUTO.pdf)、[Toshiba 二极管端子识别](https://toshiba.semicon-storage.com/us/semiconductor/knowledge/faq/diode/how-can-i-distinguish-between-the-anode-and-cathode-terminals.html)。具体料号仍以其规格书为准。

## 审查覆盖与仍然存在的限制

| 范围 | 已检查 | 后续边界 |
|---|---|---|
| XLSX/CSV/TXT 读取 | 编码、表头/内容识别、工作表、合并格、续行、来源记录 | 没有本次客户的真实源文件；`.xls` 仍需转换 |
| 配对与判定 | 料号、位号、MPN、替代、参数、语义、可关闭字段、拆分合并 | 多阶 BOM 未提供完整父项展开及单位换算；不能据汇总数量推导实际装配层级 |
| 描述参数 | 数值/单位等价、封装、型号、中文区分特征 | 特征词表有限；未知中文颜色、工艺、结构、接触方向等仍不能保证识别；没有规格书级语义模型 |
| 列识别 | 1000 份开发生成器与 400 份保留生成器评估 | 陌生 DNP 表头识别仍不充分，保留生成器的层级列识别也不是 100%；应优先增加人工列映射确认与保存模板 |
| 本地模型 | 下载状态、选择、真实加载/向量、失败、调用证据、原生 llama.cpp 路径 | 可选语言模型尚未接入；本次只实测轻量模型，不能外推到其他平台和 GPU |
| 云端 | Schema、批次、覆盖、取消、隐私、程序否决冲突 | 使用本地模拟服务验证；未调用实际云端账户。隐私选项控制结构化字段，不自动清除描述自由文本中可能出现的敏感信息 |
| 方向提醒 | 规则、来源描述、位号、筛选、详情、Excel | 未做人工勾选签核、CAD/照片校对或实际角度判定 |
| 历史与报告 | 文件副本、SHA、报告、模型调用证据、pending | 历史“重新载入并核对”使用当前规则与设置，不等于恢复当年的完整算法环境；当时报告应以保存的 XLSX 为准 |
| 更新与发布 | 工作流、版本、签名和安装代码静态检查 | Windows/Linux 更新缺独立签名校验清单；解包循环缺显式路径边界检查。此处仅报告，未改变更新协议或发布签名策略 |

优先后续事项：人工确认/修正列映射；DNP 原始值与三态“不确定”的完整建模；客户 BOM 固定回归集；再考虑把可选语言模型接入受约束的字段辅助流程。不能单纯放宽比较规则来提高 PASS 比例。

另外，更新模块仍建议单独安排维护：Windows/Linux 下载应增加可验证的签名或校验清单，解包前应规范化并限制路径在 staging 内。当前代码的这两个静态问题不应与本次 BOM/模型/方向功能已验证的结果混为一谈。
