# 智能 BOM 核对升级：代码审查与实施计划

审查对象：`main` / `dev` @ 10a26e2（v2.0.0）。日期：2026-11-07。

## 1. 现有项目

| 项目 | 现状 |
| --- | --- |
| 技术栈 | Flutter 3.47 / Dart 3.13，自绘界面（无 Material），约 9 200 行 Dart |
| 平台 | Windows x64/ARM64、Linux x64/ARM64、Android；GitHub Actions 全平台构建，`dev` 绿灯后同步 `main`，打标签发布 |
| 读表 | `core/table_reader.dart` + 自研 `xlsx_reader.dart`（兼容 T100 导出），csv/txt 编码自动识别 |

| 核对 | `core/bom_compare.dart`：以**料号相同**为匹配键；描述按英文数字参数多重集比较；用量、位号、共有其他列精确比较；无表头列按内容配对 |
| AI | `core/ai_check.dart`：OpenAI 兼容 / Anthropic 两种请求，核对后整体发给模型，返回总结与发现；结果只作说明，不参与判定 |

`core/` 不依赖 Flutter，可单测；30 个测试覆盖读表、核对规则、报告、AI JSON 解析、更新。

## 2. 与新需求的差距

| 需求 | 现状 | 差距 |
| --- | --- | --- |
| 统一中间模型（原始文件、工作表、Excel 行号、记录 ID、未知字段保留） | `BomPart` 有行号和其他列，无文件 / 记录 ID，无层级、DNP、替代、类别 | 需新建 `BomRecord` / `BomDocument` 模型 |
| 动态字段识别（合并单元格、多工作表、层级、DNP、选配） | 内容打分启发式，单工作表，不识别层级、DNP、选配 | 需要扩展 + 本地模型参与字段判断 |
| 匹配 | 只按料号相等 | 需多策略候选（位号、厂商型号、规格向量、描述语义）+ 一对多 / 多对一 + 置信度与依据 |
| 规格理解 | 英文数字 token 比较，不做单位换算 | 需参数抽取 + 程序标准化（10K = 10 kΩ，0.1uF = 100nF，容差、额定值、封装） |
| 结果状态 | 一致 / 有差异 / 仅一侧 | 需 PASS / NG / REVIEW / UNMATCHED / APPROVED_SUBSTITUTE + 证据、置信度、模式与模型来源 |
| 本地 AI | 无 | 需内置运行时与模型管理 |
| HYBRID / CLOUD_FULL | 只有「核对后整体发给 AI 写说明」 | 需不确定记录筛选、分批、交叉验证、引用校验、覆盖率校验 |
| Provider 架构 | 两种请求格式写在 `ai_check.dart` | 需统一接口 + DeepSeek / OpenAI / Anthropic / 自定义适配器，重试、限流、取消、Token 与费用统计、请求日志 |
| 密钥 | API Key 明文存于 `settings.json` | 需系统安全存储（Windows DPAPI、Android Keystore、Linux libsecret） |
| 界面 | AI 结果用紫色 | 需求禁止紫色，需改色 |
| 测试 | 固定演示文件 + 单元测试 | 需动态生成测试、带人工标注的独立测试集、按类别统计的泛化指标、三模式对比 |

## 3. 本地 AI 方案

| 用途 | 候选 | 大小（Q4_K_M） | 许可证 |
| --- | --- | --- | --- |
| 语义匹配（向量） | Qwen3-Embedding-0.6B | 约 0.4 GB | Apache-2.0 |
| 字段识别、描述理解、结构化抽取 | Qwen3-1.7B | 约 1.28 GB | Apache-2.0 |
| 运行时 | llama.cpp，经 Dart FFI 包 `llamadart`（Windows / Linux / Android，CPU + Vulkan，原生库在构建时下载） | — | MIT |

两个模型都用 llama.cpp 运行（GGUF 同时支持生成和向量），只需一个运行时，ONNX Runtime 暂不引入。最终选择以第 3 阶段在真实 Windows 笔记本上的准确率、速度和内存实测为准。

本地模型的使用方式（决定性能是否可接受）：
- 1.7B 模型**不逐行调用**。它看的是每列的表头 + 样本值，判断字段含义；对规则抽取失败或有歧义的描述做参数抽取；对多个候选的记录做判断。
- 向量模型给全部物料描述做嵌入，用于候选生成（几百行在 CPU 上约数秒）。
- 数值、单位、容差、数量、位号由程序严格校验；模型结论不能推翻程序确认的硬冲突。

## 4. 主要风险

1. **小模型准确率**：1.7B 模型的结构化输出可能不稳定。对策：约束 JSON 语法（llama.cpp grammar）、程序校验每个引用、不确定一律 REVIEW。达不到要求时换 Qwen3-4B（约 2.5 GB）作为可选模型。
2. **体积**：两个模型共约 1.7 GB。打进安装包后 Windows 安装包从约 30 MB 变成约 1.8 GB；Android APK 不可行。
3. **速度**：无 GPU 的办公电脑上 1.7B 生成约每秒 10–30 token；大型 BOM 需要靠「只在必要处调用」控制时间，并显示进度、可取消。
4. **Android**：手机运行 1.7B 内存与发热压力大。
5. **测试集**：「不同公司、带人工确认答案」的真实 BOM 我无法凭空生成。可以收集公开的开源硬件 BOM（KiCad / Altium 导出，许可允许），程序先给出候选答案，再由你确认；你提供的客户 BOM 只在本机使用、不进仓库。
6. **CLOUD_FULL 的大 BOM**：需分批 + 全局整合，每批结果都要做覆盖率和引用校验，失败批次标记未完成，不显示「核对完成」。

## 5. 实施阶段

每个阶段在 `dev` 上交付可运行代码 + 测试结果 + 问题记录（本目录下 `phase-N.md`），CI 全绿后同步 `main`；发布版本仍等你指示。

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| 1 | 统一中间模型 `BomDocument` / `BomRecord`（来源文件、工作表、行号、记录 ID、原始字段全保留、层级、状态标志） | 现有功能迁移到新模型后测试全部通过 |
| 2 | 动态字段与物料识别：多工作表、合并单元格、层级、DNP / 选配 / 替代、物料类别、未知字段保留 | 动态生成的表格变换下字段识别稳定 |
| 3 | 本地 AI 集成：`llamadart`、模型管理（下载 / 校验 / 版本 / 状态）、字段判断与参数抽取提示词、向量 | 真实模型推理；Windows 实测速度、内存记录在案 |
| 4 | 候选匹配 + 参数标准化与严格校验，五种结论状态，依据与置信度 | 注入差异全部检出、等价变换不误报 |
| 5 | HYBRID：不确定记录筛选、云端补充、交叉验证、失败保留本地结果 | 证明云端解决了本地 REVIEW 的记录 |
| 6 | CLOUD_FULL：云端独立识别与匹配、分批、覆盖率与引用校验 | 不依赖本地匹配；截断 / 失败不显示完成 |
| 7 | Provider 抽象与适配器（DeepSeek / OpenAI / Anthropic / 自定义）、安全存储、重试限流取消、Token 与费用、请求日志 | 各适配器离线模拟测试 + 真实连接测试 |
| 8 | 统一结果结构与报告：证据展示、按物料 / 位号 / 异常 / 风险筛选、Excel 导出；界面加模式选择、模型状态、任务进度 | 未检查完的记录不可能显示全部通过 |
| 9 | 动态测试生成器、独立测试集、按类别 / 结构 / 语言统计的泛化报告、三模式对比、回归测试进 CI | 指标报告随每次修改自动生成 |
| 10 | Windows 安装包集成、首次运行模型准备、性能优化 | 干净 Windows 机器上安装即用 |

阶段 1、2、4 不依赖模型下载方式，可以先做；第 9 阶段的生成器会从第 2 阶段开始逐步建立，用来验证每一步。

## 6. 已确定的决定（2026-11-07）

| 问题 | 决定 |
